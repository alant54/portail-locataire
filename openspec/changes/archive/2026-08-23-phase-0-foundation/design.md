## Context

Greenfield repo in a devcontainer with Node 22, SQLite and port 5173 forwarded. The ERP (see `docs/PLAN.md` §2 for verified facts) returns `{data, meta}` pages, keys rows by UUID `id` with a human `external_ref`, and detail endpoints accept only `external_ref`. Three agents will work in parallel right after this change; see proposal.md – Why.

## Goals / Non-Goals

**Goals:**
- A skeleton that boots with `npm run dev` and a DB that migrates and seeds in one command.
- A schema and type layer complete enough that no lane needs to touch them.
- Fixtures that let lanes B and C ignore lane A entirely.

**Non-Goals:**
- Any real sync logic, auth logic, or UI beyond layout/nav (those are the lanes).
- Visual polish.

## Decisions

- **Next.js App Router + TypeScript**, single process. Alternative: separate API + Vite SPA — rejected, it doubles the surface the agents must agree on. Route groups `src/app/(tenant)` and `src/app/(admin)` give each lane a disjoint folder.
- **better-sqlite3 + Drizzle ORM**, schema in `src/db/schema.ts`, migrations generated by `drizzle-kit` into `drizzle/`. Alternative: Prisma — heavier, slower iteration. Raw SQL — fine for sync but worse for lanes B/C.
- **Mirror tables keep ERP UUID as PK and `external_ref` unique.** Sync events reference UUIDs; the UI and tickets reference `external_ref`. Storing both avoids any lookup trip to the ERP.
- **Ticket rows denormalise `tenant_ref`, `lease_ref`, `unit_ref`** (the refs the brief asks to keep) rather than UUIDs, so tickets survive a full re-sync and read well in the admin inbox.
- **Cross-lane interfaces as stubs now**: `getCurrentTenant()` returns the first fixture tenant; `runIncrementalSync()` returns a fake summary. Lanes replace bodies, never signatures. The two return shapes live in `src/contracts.ts` so neither seam's type is owned by the lane that implements it, and a contract test in `npm test` fails if a lane narrows one. Alternative: let each lane export its own type — rejected, it makes the consumer depend on the implementer's folder, which is exactly what the worktree split is meant to avoid.
- **One test database per suite** via `src/db/test-db.ts` (migrate a fresh file per suite, seed fixtures on request). Alternative: share `data/app.db` — rejected, three worktrees running `npm test` would clobber each other's rows and the failures would look like logic bugs. Deciding this in Phase 0 also means the lanes' tests are mergeable in Phase 2.
- **Fixtures pulled from the real ERP** with a one-off script (`scripts/pull-fixtures.ts`) and committed as JSON; the seeder writes through the same upsert helper the sync will use (`src/db/upsert.ts`) so fixture and sync rows are byte-identical.
- **Worktrees**: `lane-a`, `lane-b`, `lane-c` branches from `main` after this change; `schema.ts`/`types.ts` edits go through `main` and are merged down.

## Risks / Trade-offs

- [Schema mistake discovered mid-lane] → the human owns the schema; fix on `main`, merge into all worktrees, Drizzle regenerates a migration.
- [Fixture tenants too boring for the demo] → `pull-fixtures` selects tenants with an active lease, non-zero balance and an upcoming maintenance.
- [`better-sqlite3` native build in the devcontainer] → `build-essential` is installed in the image; verify in task 1.
- [A lane needs a package Phase 0 did not install] → the dependency list is frozen with the schema; the lane asks on `main` and the install is merged down, rather than three worktrees each editing `package.json`.
- [ERP shape drifts from `docs/erp/openapi.json`] → types are derived from live sample records in the pull script; snapshot date noted in PLAN.md.
